# Issue: Atlas 分支回放器

## Goal

在全屏 Branch Atlas 中回放当前活跃终点的决策路径，让用户按有意义的会话事件重走一条分支历史。

## 背景/问题

静态拓扑能展示结构，但无法表达会话如何逐步抵达当前分支。直接逐条播放全部 JSONL entry 会产生无意义的高频闪烁；回放必须以分支路径上的语义事件为节拍，并在真实 fork 处说明存在替代路线。

## 验收标准 (Acceptance Criteria)

- [ ] WHEN 用户打开 Atlas，系统 SHALL 提供播放、暂停、单步、速度和进度拖拽控件。
- [ ] WHEN 回放运行，系统 SHALL 沿当前活跃终点的 parentId 路径按语义事件顺序推进，并将当前节点聚焦到地图与 Inspector。
- [ ] WHEN 到达真实 fork，系统 SHALL 短暂显示候选分支并继续当前活跃路径，不修改用户选择的分支。
- [ ] IF 用户手动选择节点、拖拽进度或关闭弹窗，THEN 系统 SHALL 暂停回放并保持当前位置。
- [ ] WHERE 会话为大文件，系统 SHALL 只使用已构建的 branch model，不重新扫描或重新解析 JSONL。

## 实施阶段

### Phase 1: 规划和准备
- [x] 复用 `buildPath()`、`focusUid`、`selectedUid` 与 Atlas Inspector 的现有契约。
- [x] 确定回放粒度为语义 checkpoint，而非每条原始 entry。

### Phase 2: 执行
- [ ] 建立纯 replay path / checkpoint 选择器与单元测试。
- [ ] 实现可暂停的 replay 状态机、速度和拖拽定位。
- [ ] 在 Atlas header / selection dock 中接入控制条与 fork 提示。

### Phase 3: 验证
- [ ] 单元测试：路径、速度、暂停、结束、fork checkpoint。
- [ ] 集成测试：Atlas 控制状态和节点聚焦。
- [ ] 手动验证：真实大型 Pi session 的播放与关闭清理。

### Phase 4: 交付
- [ ] 创建 PR 记录变更、验证与回滚方式。

## 关键决策

| 决策 | 理由 |
|------|------|
| 回放当前活跃终点路径 | 保持回放可理解，不把所有历史分支混成一条时间流。 |
| checkpoint 使用 user、assistant reply、tool、fork、error、compaction | 保留决策节拍，避免数千条原始 entry 造成视觉噪声。 |
| fork 只提示不自动换路 | 回放不应篡改用户当前活跃分支。 |
